# inlay

TypeScript package (`inlaycms`): a code-first CMS for content sites. Inlay is the whole server: a site is a signed release (its templates, schemas, shipped content and routes), pushed to a host running `inlaycms serve`, previewed and then activated. A content core on SQLite (better-sqlite3 + Kysely) with schemas defined in Zod, plus the public site, admin, MCP server, release host and CLI built on top, running on Fastify 5. Node >= 24, ESM.

Design and plans: `docs/superpowers/specs/` and `docs/superpowers/plans/`. The design is still in progress, so treat the spec as the source of truth over this file.

## Commands

- Package manager is pnpm (pinned in `package.json` `packageManager`). Don't use npm in this repo: there is no `package-lock.json`. The one exception is pack-test, whose fresh site installs with npm on purpose, the way most sites will.
- `pnpm test`: vitest, runs `tests/**/*.test.{ts,tsx}`. Run a single file with `pnpm test tests/core/save.test.ts`. A global setup builds the admin assets first if `assets/admin/` is missing.
- The host tests that spawn real processes (`tests/host/{serve,dev,swap}.test.ts`) can hang when a `cluster` child leaks. Wrap test runs in `timeout` (`timeout 600 pnpm test <files>`), run those three files one at a time under `timeout 300`, and check `pgrep -af "bin.ts (serve|dev)"` afterwards.
- `pnpm run typecheck`: `tsc --noEmit` over `src`, `tests`, `example` and `client`.
- `pnpm run build`: runs `build:admin`, then emits `dist/` via `tsconfig.build.json` (`src` only).
- `pnpm run build:admin`: bundles `client/admin/` into `assets/admin/` (`scripts/build-admin.mjs`).
- `pnpm run dev`: watches the admin assets and runs `inlaycms dev --config example/inlay.config.ts` at `http://localhost:3000` (data in `example/data/`; restarts on changes in `example/`, and on changes in `src/` through `tsx watch`).
- `pnpm run example:check`: runs the CLI's `check` against `example/inlay.config.ts`.
- `pnpm run example:pack`: packs the example into a signed release at `example/data/release.tgz` with the development key in `example/keys/`.
- `docker compose run --rm pack-test`: packs the tarball, installs it into a fresh copy of `example/`, packs and activates the example's release into a fresh data folder and smoke-tests `inlaycms serve` and the CLI (`scripts/pack-test/`). `docker compose up serve` runs the host image (`Dockerfile`: the packed tarball installed with production dependencies only, `inlaycms` on the `PATH`, data in a volume at `/data`). The compose services `test`, `dev` and `pack-test` build from `Dockerfile.dev`, which is only for working on Inlay.
- `pnpm run image`: builds the Inlay image (`Dockerfile`) tagged `inlaycms`: the host and the whole CLI, with TypeScript, so a site needs no Node. `docker/inlaycms` is the host-side wrapper that runs the CLI through the published image (`ghcr.io/donstephan/inlaycms`, or `INLAY_IMAGE`) on the current folder (shipped in the image at `/opt/inlaycms/wrapper/inlaycms`). `pnpm run image:test` (`scripts/image-test.sh`, runs on the host: Docker and bash only) builds the image and drives the wrapper against a copy of `example/` with no `node_modules`.
- The `inlaycms` CLI from source: `pnpm exec tsx src/adapters/cli/bin.ts <command>`. `check [--db] [--export]` validates a site's code (and, with `--db`, dry-runs it against a database); `keygen` makes a signing key pair; `pack --key [--out]` builds a signed release; `backup`, `restore-backup`, `export`, `import [--dry-run]` and `create-owner` work on a site's database or a host's data folder. `dev [--config] [--port]` runs a site from source with watch and restart; `serve` runs the host from `INLAY_DATA_DIR` (settings are `INLAY_*` environment variables, see `src/host/config.ts`); `activate <file|id> [--data]` makes a release live offline; `releases [--data]` lists them. `push <host> [--file] [--activate] [--dry-run] [--token]` sends a release to a running host through the push API (`src/adapters/cli/remote.ts`), and `activate <host> <id>` and `releases <host>` are the remote forms (a first argument starting with `http://` or `https://`); `create-token --email --name [--push] [--data]` mints an API key (a push token with `--push`) offline; `reset-password --email [--data]` sets a new password for a user offline (read from the terminal or stdin) and ends their sessions and keys.

## CI and releases

- `.github/workflows/ci.yml` runs on pushes to `main` and on pull requests: typecheck and the test suite, pack-test and image-test. pack-test runs through `docker build`/`docker run` rather than compose, because compose's default network (`inlay-dev`) is external and only exists on a dev machine.
- `.github/workflows/release.yml` runs on a `v*` tag. It fails unless the tag matches `version` in `package.json`, runs `ci.yml`, then stages the package on npm and pushes the image to `ghcr.io/donstephan/inlaycms` (`X.Y.Z`, `X.Y` and `latest`; a prerelease gets only its version, and npm's `next` tag). To release: bump `version`, commit, push the tag, then approve the staged version on npmjs.com (Staged Packages, with 2FA). Nothing is installable from npm until it's approved; the image goes out as soon as CI pushes it.
- npm publishing uses trusted publishing (OIDC) with `npm stage publish --provenance`: no npm token exists anywhere. The trusted publisher allows only staging, not `npm publish` or `npm dist-tag`, so CI can't ship or move `latest` without the owner's approval. Don't add npm tokens to the workflows or to the toolbox.
- The `Dockerfile` build stage runs on `$BUILDPLATFORM` (it only produces the tarball), so the arm64 image builds only its final `npm install` under emulation.

## Layout

- `src/index.ts`: the public API. Anything exported here is public. `tests/public-api.test.ts` tests through this entry point, and also checks the `inlaycms/site` and `inlaycms/testing` export lists.
- `src/site.ts`: the `inlaycms/site` entry point, what a site's code imports (the `define*` functions, fields, `defineConfig`, `defineRoute`, the types templates, routes and migrations use). It must export nothing that reaches the server; `inlaycms pack` enforces that import boundary (`src/core/release/bundle.ts`).
- `src/testing.ts`: the `inlaycms/testing` entry point (`createTestSite`), route tests for a site: `loadConfig` and `createSiteApp` in a temporary data folder, requests through `inject`. Server-side, so `inlaycms pack` refuses it in site code.
- `src/core/`: the content core, with no HTTP. Grouped by area: `content/`, `db/`, `registry/` (the `define*` functions), `fields/`, `richtext/`, `media/`, `redirects/`, `auth/`, `agent/`, `backup/`, `export/`, `site/`, `site-lock/`, `messages/`, `release/` (signing keys, the release manifest, `packRelease` and `readRelease`). `boot.ts` runs startup (system migrations, shipped content), `check.ts` dry-runs that on a snapshot for `inlaycms check --db`, `report.ts` holds the boot and `inlaycms check` report, `preview.ts` signs preview tokens, `theme.ts` resolves and contrast-checks the admin theme, `archive.ts` extracts tarballs safely, and `core.ts` assembles the core. Shared types go in `src/core/types.ts`.
- `src/core/db/migrations/NNNN_name.ts`: system migrations. Each one must also be registered by hand in `src/core/db/migrate.ts`.
- `src/adapters/`: everything that faces the outside. `site/` (the Fastify plugin in `plugin.ts`, used internally by `createSiteApp`; rendering, caching, preview, site lock, backup schedule, the release's routes in `routes.ts` and its `/public/*` files in `public.ts`), `admin/` (server-rendered admin screens and forms; `screens/releases.tsx` is the owner's Releases screen, which works without a host and gains preview and activation through `AdminHostHooks`), `mcp/` (MCP server and tools), `auth/` (better-auth handlers), `cli/` (`bin.ts` is the `inlaycms` binary). `web.ts` holds the Fastify-to-Web `Request`/`Response` helpers (headers, cookies, same-origin checks) shared by the auth, admin and site adapters.
- `src/host/`: the release host. `config.ts` (`INLAY_*` environment to `HostConfig`, the data folder), `store.ts` (releases on disk and the `releases` table), `activate.ts` (the activation transaction), `app.ts` (`createSiteApp`, the Fastify app for one site, shared by serve, dev and tests), `primary.ts`, `worker.ts`, `ipc.ts` and `serve.ts` (`inlaycms serve`: a `cluster` primary supervising one worker per release), `bin.ts` (the file each worker and dev child starts from), `push.ts` (the push API), `diff.ts` (the release diff shown on push and in the admin), `preview-worker.ts` and `preview-proxy.ts` (a staged release served for preview), `dev.ts` (`inlaycms dev`: a forked child per run, restarted on file changes), `hooks.ts` (`AdminHostHooks` and `adminHostHooks`: what the admin's Releases screen asks of `inlaycms serve`, built by `createSiteApp` when it has a host; `inlaycms dev` passes none).
- `src/jsx/`: Inlay's own JSX runtime, used for templates and the admin. `src/config.ts`: `defineConfig` and config loading for the CLI. Loading bundles the config and the site with esbuild (`bundleConfig` in `src/core/release/bundle.ts`), with every `inlaycms` import and every file of Inlay's own pointing at the running copy, so a site needs no tsx and never gets a second copy of Inlay.
- `client/admin/`: the admin's browser CSS and JS. Built into `assets/admin/`, which ships in the package.
- `example/`: the example site, also used by `dev`, tests and pack-test. It has no app of its own: it runs through `inlaycms dev` and, packed, `inlaycms serve`. `inlay.config.ts` points the CLI at it, `site.tsx` defines it, `public/` holds its static files, `content.ts` holds its shipped content, `routes.ts` its `/contact` route, `migrations.ts` its migration functions, and `keys/` a development-only signing key pair.
- Tests live under `tests/` by area: `core/`, `admin/`, `auth/`, `cli/`, `host/`, `jsx/`, `mcp/`, `site/` and `testing/`, mostly one file per feature; `example.test.ts` and `example-release.test.ts` at the top level cover the example site. Helpers are in `tests/helpers/`. `core.ts` `makeCore()` gives you an in-memory DB with a deterministic clock plus `owner` and `editor` contexts, and `app.ts`, `admin.ts`, `auth.ts` and `mcp.ts` cover the adapters. Fixtures live in `tests/fixtures/`. `tests/setup/` holds the vitest global setup and setup files.

## Conventions

- Relative imports use the `.js` extension (NodeNext). Use `import type` for type-only imports.
- TSX uses `jsxImportSource: 'inlaycms'`. Tests and `tsconfig.json` alias `inlaycms` to `src/index.ts`, `inlaycms/site` to `src/site.ts` and `inlaycms/testing` to `src/testing.ts`.
- No semicolons, single quotes, 2-space indent. Exception: files under `src/core/db/` use semicolons, so match the file you're in.
- Strict TS with `noUncheckedIndexedAccess`, so handle indexed access explicitly.
- Throw `InlayError(code, messageId, params, details)` from `src/core/errors.ts`, not plain `Error`. Any user-facing text goes in `src/core/messages/en.ts` as a message ID and is never inlined. Messages are written in plain language for non-technical editors.
- Vitest globals (`describe`, `it`, `expect`) are enabled, and most tests use them without importing.
